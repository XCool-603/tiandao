# 多角色流水线协同交付 (Multi-Role Delivery Pipeline)

本规范用于通过多智能体角色流水线方式高效交付软件工程或复杂系统。
特别针对自建或中转大模型服务器（如私有 vLLM/Ollama/OneAPI 集群），内置了**严格的并发控制与防打崩保护机制**。

---

## 核心原则：防服务器过载保护 (Anti-Crash Guardrails)

> [!CAUTION]
> **私有服务保护红线**：绝不并发多角色同时请求 API！
> 过去曾出现多个项目同时触发多角色流水线导致后端服务器（如自建 API 端口）瞬间 OOM、连接耗尽或服务崩盘的情况。

1. **严格单并发串行 (Strict Serial Execution)**：
   - 角色必须严格按照流水线阶段顺序执行：`PM -> Architect -> Dev -> QA -> Release`。
   - 同一时刻只允许一个角色激活并向模型发起交互。
2. **请求节流冷却 (Request Pacing)**：
   - 每个角色的主生成调用结束后，强制等待 1~2 秒，避免瞬时高频打满后端连接池。
3. **上下文蒸馏传递 (Context Distillation)**：
   - 严禁将前序所有角色的完整对话历史直接塞给下一个角色。
   - 下游角色仅接收上游角色生成的**核心标准化产出物（Artifact/文档）**，节省 70% 以上 Token 与显存占用。
4. **容错重试与指数退避 (Exponential Backoff)**：
   - 遇到 `429 (Rate Limit)`、`502/504 (Bad Gateway/Timeout)` 或连接重置时，执行退避等待（5秒 -> 10秒 -> 20秒），严禁并发重试。
5. **阶段成果即时持久化 (Stage Checkpoints)**：
   - 每个阶段完成即把产出物写入本地文件（如 `.delivery/stage_*.md`），确保随时可断点续接。

## 五大流水线角色与职责

| 阶段 | 角色名称 | 核心职责 | 核心交付物 |
| :--- | :--- | :--- | :--- |
| **阶段 1** | 🎯 **产品需求经理 (PM)** | 澄清用户目标、梳理用户场景、确定功能边界与非功能需求 | `01_PRD_需求规格.md` |
| **阶段 2** | 🏛️ **系统架构师 (Architect)** | 技术选型、模块划分、数据结构定义、API/函数接口契约 | `02_ARCHITECTURE_架构设计.md` |
| **阶段 3** | 💻 **核心开发工程师 (Dev)** | 依契约逐步落地代码、处理边界情况、遵循工程规范 | 业务源代码文件 |
| **阶段 4** | 🧪 **质量测试工程师 (QA)** | 编写测试用例、执行功能测试/脚本测试、验证缺陷与修复 | `03_TEST_测试报告.md` |
| **阶段 5** | 📦 **交付负责人 (Release)** | 组织部署启动脚本、编写使用说明、输出交付总结 | `04_DELIVERY_交付总结.md` |

## 流水线标准化执行流程

### 阶段 1：【需求澄清与规格制定】（PM 角色）
1. 梳理用户的原始需求输入。
2. 明确交付目标（MVP 核心功能、次要功能、排除范围）。
3. 输出标准化文档 `.delivery/01_PRD_需求规格.md`，包含：
   - 用户核心价值与目标
   - 功能清单与优先级 (P0 / P1 / P2)
   - 异常边界与约束条件
4. **流转动作**：向用户简要汇报需求确认点，随后移交下一阶段。

---

### 阶段 2：【系统架构与契约制定】（Architect 角色）
1. 读取 `01_PRD_需求规格.md`。
2. 制定系统技术栈、文件目录结构与关键数据流。
3. 严格定义核心接口/数据结构的输入输出契约。
4. 输出 `.delivery/02_ARCHITECTURE_架构设计.md`，包含：
   - 项目目录树结构
   - 核心模块划分与职责
   - API / 数据契约 Schema
   - 依赖项清单
5. **流转动作**：冷却 1 秒，移交下一阶段。

---

### 阶段 3：【模块化实现落地】（Dev 角色）
1. 读取 `02_ARCHITECTURE_架构设计.md`。
2. 按照架构契约分模块编写代码：
   - 优先编写基础数据结构与配置；
   - 接着编写核心逻辑业务层；
   - 最后编写外部交互/展示层。
3. 遵循代码健壮性原则，补充必要注释与异常处理。
4. **流转动作**：冷却 1 秒，移交下一阶段。

---

### 阶段 4：【质量验证与测试】（QA 角色）
1. 读取源代码与架构契约。
2. 编写或执行验证测试：
   - 单元测试 / 冒烟测试脚本；
   - 运行项目验证是否有语法错误、未定义变量或接口不匹配；
   - 验证边界条件（空输入、异常网络等）。
3. 若发现问题，直接原地进行修复并重新验证。
4. 输出 `.delivery/03_TEST_测试报告.md`，记录验证结果。
5. **流转动作**：冷却 1 秒，移交最终阶段。

---

### 阶段 5：【交付封装与验收】（Release 角色）
1. 验证项目整体可运行性。
2. 编写或完善 `README.md` 与一键启动脚本（如 `start.bat` / `start.ps1` / `run.sh`）。
3. 汇总全流程成果，向用户输出完整的交付报告：
   - 项目概要与完成情况清单
   - 快速启动与验证命令
   - 后续演进建议与注意事项

## 快捷使用示例

当用户输入：
```text
/multi-role-delivery <你的任务或需求>
```

执行流程：
1. 系统自动在工作区创建 `.delivery/` 归档目录。
2. 切换至 **PM 角色**，生成 `01_PRD_需求规格.md`。
3. 冷却缓冲后，切换至 **Architect 角色**，生成 `02_ARCHITECTURE_架构设计.md`。
4. 切换至 **Dev 角色**，落地代码。
5. 切换至 **QA 角色**，运行测试并生成 `03_TEST_测试报告.md`。
6. 切换至 **Release 角色**，完成交付并向用户汇报。
